# 网络事件与自适应监控设计

## 目标与已选方案

用户同意采用“事件触发＋自适应定时兜底”，降低正常联网期间的重复探测，同时保留无人值守故障发现和恢复能力。

已比较的方案：纯定时检测简单但重复工作较多；纯事件监听无法可靠覆盖 Wi-Fi 仍关联但上游不可达的情况；采用事件监听与低频主动检测结合，并在异常期间缩短复核间隔。

## 具体行为（实现建议）

- 前台与 Guardian 使用同一个引擎实现，不增加第二个监控控制者。
- 启动时执行完整检查。正常期间的轻量检查默认每轮结束后等待 90 秒；异常复核等待 10 秒。探测耗时另计。
- 保留现有 CheckIntervalSeconds 字段作为正常检测间隔，保留用户已保存的显式值；新配置默认 90 秒。已有配置若为 30 秒，仍保留 30 秒，可在现有策略页调整。
- 异常复核间隔取正常间隔和 10 秒的较小值，避免修改为比用户配置更慢。策略页说明正常周期与异常复核的关系。
- 监听 .NET NetworkChange 的网络可用性和地址变化事件，合并短时间连续事件，首次事件后 1 秒触发检查，后续事件不得无限推迟。
- 检查进行中收到事件，最多保留一次后续检查请求；停止、释放资源后不再触发。事件检查与定时、手动检查共用现有互斥和取消机制。
- 监听从监控启动持续到停止，停止时取消订阅；订阅失败记录原因并继续定时兜底，不终止守护。
- 健康时的轻量检查读取接口状态并使用已配置的 HTTPS 目标确认互联网连通性，沿用现有至少两个目标成功的判定规则；省去主动网关 Ping、独立 DNS 探针及系统命令诊断。HTTPS 本身仍可能涉及 DNS 与 TLS。
- 轻量检查失败、网络事件、首次启动、手动检测及异常复核均执行完整诊断；恢复动作后的验证继续使用现有完整诊断。
- 轻量失败只触发诊断，不单独累计失败次数。完整诊断确认失败后，每轮仅累计一次，继续遵循既有失败阈值、冷却时间与高风险恢复限制。
- 轻量成功只能更新其实际检测的结果，不能把旧网关/DNS诊断标为刚完成；界面和日志区分轻量与完整检查。下一次检测倒计时显示实际调度时间。
- 轻量恢复为健康后回到正常间隔。完整恢复流程结束后的调度必须依据最新验证结果，避免沿用恢复前的失败状态。

## 涉及模块

- Core/Monitoring：事件来源抽象、Windows 网络事件适配、自适应调度、合并及生命周期。
- Core/Connectivity：轻量检测入口，复用现有 HTTPS 探针与成功门槛。
- Core/Models、Localization：默认周期、结果来源及中英文说明；不扩展恢复权限。
- App、Guardian：连接事件来源、展示和记录检查类型，后台热加载继续更新调度。
- tests：调度、探针、设置兼容、界面结果来源和生命周期回归。
- README：使用方式、资源开销与检测延迟说明。

## 验证与交付

1. 先编写并运行失败回归：健康周期、异常加速、恢复回退、策略热更新、事件合并、检查中事件、停止取消与解除订阅。
2. 验证轻量健康不执行完整诊断；轻量异常执行完整诊断且只累计一次；多个探针的成功门槛保持一致。
3. 验证前后台使用相同行为，手动检测仍完整，已有周期配置不被覆盖，旧诊断不误报为新结果。
4. 运行完整解决方案测试、构建和 git diff --check，记录命令、退出码及任何失败。
5. 提交前检查 git status 和 git diff，仅暂存本任务相关文件，以中文提交；保留已有 docs/2026-10-18-validation.md 未提交改动。

本轮实现和验证不注入真实断网、不停止正在运行的后台、不替换已安装程序。交付时明确区分代码完成与现场启用状态；CPU、内存及流量下降幅度需实际测量后才能报告。
